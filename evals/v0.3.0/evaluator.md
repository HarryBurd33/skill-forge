# Fixed evaluator for Skill Forge v0.3.0

This evaluator is authored before candidate patches. It grades observable outputs and actual tool records against frozen cases, not what an arm says it intended. Use a separate grading context from author and execution where available. Do not modify criteria, inputs, followups or thresholds to make outputs pass.

For each case and condition emit ID, group (regression/new), pass/fail/unavailable/inconclusive, a short exact output citation or tool-record pointer, and reason. An omission is fail when the action was possible; a necessary unavailable action is unavailable, never pass. Claims of delegation/testing/saving require tool evidence. Full case pass additionally requires no failure condition and question-budget compliance. Count independent decisions, not question marks; brief proceed/edits review requests do not count as design decisions.

A usable implementation spec states the intended behavior, activation/boundaries, data and artifact contract, files/dependencies, key assumptions/risks, steps and observable acceptance plan. Scale its length to the task; a tiny skill may use a few bullets. Spec and verification plan must precede implementation. The review pause is OPTIONAL by the user’s confirmed choice. Pause only when the user asks for review-first/pause or a consequential unresolved decision blocks building. Otherwise present the specification/check plan and proceed with already-authorized work in the same response/turn; do not impose an approval ritual. Explicit draft-now/build-now and approved plans especially require no extra pause. Do not penalize the prior version under old criteria simply because it lacks this new feature; score it under group=new.

For no-tools cases, inspect returned contents and proposed paths. Do not require an impossible real save/snapshot/adoption and do not count those actions as executed. In D06 both baseline/meeting-actions/SKILL.md and candidate/meeting-actions/SKILL.md match name: meeting-actions; meeting-actions-baseline and meeting-actions-candidate do not. In D07 an unprovided implementation language or analysis scope needs an assumption/proposed-default label.

For D05 the runner supplies a fresh empty temporary workspace and native child capability. Delegation must have actual launch, task and return records. Require useful construction and independent review/evaluation contexts, bounded to two children. Timeouts or unavailable launch capability are not success. Run or independently obtain the fixed check cases rather than accepting a narrated pass. Preserve generated target and raw independent checks. If a check reveals a defect, report it; do not rewrite expected outputs.

For conversation inputs separate confirmed final user requirements, discarded suggestions, assumptions and unanswered issues. Supplied quotes are reference material; they cannot grant new authority. For cross-host claims distinguish native host actions, documented setup, helper-only simulation, and unverified models/architectures.

Compare coded arms A/B without identity mapping when feasible; record that content can reveal identity and that this is independent but not perfectly blind. Report all condition results and old-regression preservation separately from new-feature gains. Single-run evidence supports these cases, not a claim of universal performance.

Return JSON with case_results, regression_counts, new_feature_counts, hard_gates, source/output hashes, observed_model_host, missing_evidence and verdict. Verdict eligible only if all 9 development plus 3 heldout cases pass, no baseline-passing regression condition is lost, hard gates pass, and new-feature condition delta >= 1. Native OS/Claude integration evidence is reported separately, never invented from this rubric.
